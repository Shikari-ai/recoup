# AI judgment: where a model is the right tool, and where it is not

Razorpay's rubric asks for "the right tool in the right place, **and where you
chose not to use one**." This document is the second half of that answer,
written first, because it was the harder decision.

Recoup has three distinct kinds of intelligence in it, and only one of them is
a language model:

| Layer | Mechanism | Why this and not something else |
|---|---|---|
| Failure classification | Lookup table | Finite, documented, must be deterministic |
| Recovery probability | Logistic regression | Needs *calibrated* numbers, and readable ones |
| Compliance | Plain code | Must be provable, not probable |
| Unmapped error triage | **LLM** | Open-ended natural language |
| Message composition | **LLM** | Tone, language, channel — genuine generation |

---

## Where a model is *not* used, and why

### Compliance gates — never, under any circumstance

`recoup/guardrails.py` contains no model call and never will. Nineteen gates
decide whether an action may execute: card-scheme retry caps, RBI pre-debit
notice, AFA thresholds, TRAI quiet hours, DND, comms frequency, stopping rules,
spend caps, killswitch.

The reasoning is not that models are unreliable in general. It is that this
layer exists to provide a *guarantee*, and a probabilistic system cannot
provide one. "The model has never permitted an unauthorised debit in testing"
is a fundamentally weaker statement than "an unauthorised debit is unreachable
in the code", and only the second is worth anything to a risk team.

There is a second reason, subtler and just as decisive: **guarantees must be
testable**. Because these gates are code, `tests/test_adversarial.py` can run a
policy whose entire objective is to breach them and assert that not one attempt
gets through. You cannot write that test against a prompt.

### Failure classification — a dictionary, not a model

Gateway error reasons are a finite, enumerated, documented set. Mapping
`insufficient_funds` to a recovery strategy is a dictionary lookup. Routing that
through an LLM would make the hottest path in the system slower, more
expensive, non-deterministic and unauditable — you could not tell a merchant
why their customer was retried, because the answer might differ between runs.

The table gets **97.6%** of held-out events exactly right. The model's job is
the remaining 2.4%.

### Retry timing and action choice — statistics, not a model

"When should I retry an insufficient-funds decline?" is an optimisation over
observed outcomes, not a language problem. An LLM asked this question will
produce a fluent, plausible, confidently-stated answer with no relationship to
this merchant's actual data.

Logistic regression instead — and specifically *not* something bigger. The
policy does not need a ranking of actions; it needs calibrated probabilities,
because it multiplies them by rupee amounts. A model that ranks perfectly but
says 0.9 where the truth is 0.4 will chase receivables that were never coming
back, and the error compounds across a batch. Measured ECE is **0.013**.

The second reason is explainability. Every coefficient is readable, and
`contributions()` returns the *exact* signed decomposition of the logit — not
an approximation like SHAP, because the logit genuinely is the sum of those
terms. When the agent debits someone, the audit trail names the features that
drove it. A gradient-boosted ensemble would likely gain a little AUC and cost
all of that. For a system that has to explain itself, that is a bad trade.

### Explanations — generated by the decision process, not narrated afterwards

`Decision.rationale` is assembled deterministically from the policy's own
arithmetic. It would have been easy to hand the decision to an LLM and ask for
a nice paragraph. That produces an explanation generated by a *different
process* than the decision — which is not an explanation, it is a
plausible-sounding narration that can drift from what actually happened. The
failure mode is a system that reliably explains decisions it did not make.

## Where a model *is* used, and why it earns its place

### 1. Triage of unmapped error codes — `recoup/llm/triage.py`

**The problem.** Real gateways ship new reason codes without warning, localise
them, and sometimes return free text. In the simulated feed ~2.4% of events
carry a string the table cannot match, including `"Kripya baad mein prayaas
karein"` — Hinglish for "please try again later", which is an
issuer-availability message. A table cannot read that. A model can. This is
open-ended natural language mapped onto a fixed concept set, which is exactly
what language models are for.

**The constraints, because a mistake here is an unauthorised debit.** If the
model reads `mandate_revoked` as `insufficient_funds`, the agent re-presents a
debit the customer explicitly cancelled.

- Output is a **closed enum**. Anything else becomes `UNKNOWN`.
- **Confidence floor** (0.70). Below it, the conservative profile stands.
- **Capped budget.** A model-assigned class gets at most 1 debit attempt where
  a table-assigned one might get 4.
- **Terminal suggestions need no confidence bar** — being told to stop is the
  safe direction.
- **Guardrails are downstream and untouched.** Nothing here can widen them.
- **Provenance is recorded** (`llm:claude:conf=0.87`) into the ledger, so a
  reviewer can always distinguish a model's opinion from a fact.
- **Failure degrades.** A timeout returns `UNKNOWN`, and recovery continues. An
  engine that stops recovering revenue because an inference API is having a bad
  afternoon has its dependencies backwards.

**The part I would defend hardest: it is not in the hot path.** Results are
cached by normalised code, so each novel string costs one call ever, and
`promote_candidates()` exports what was learned as ready-to-paste table entries
for a human to approve:

```python
"acq_deny_2201": FailureClass.INSUFFICIENT_FUNDS,   # conf=0.97
"npci_xc_09":    FailureClass.ISSUER_DOWN,          # conf=0.97
"card_vault_miss": FailureClass.TOKEN_EXPIRED,      # conf=0.97
```

The model's job is to **grow the lookup table**, not to sit in the request path
of every payment forever. After promotion the mapping is free, instant and
permanent. That is the difference between using AI as a tool and using it as a
dependency.

### 2. Message composition — `recoup/llm/copy.py`

**The problem.** The right words for "your autopay bounced" differ by failure
class (a bank outage is our fault, insufficient funds is awkward, an expired
card is neither), by language (a large share of Indian payers read Hinglish
more comfortably than formal English), and by channel (160 characters of SMS is
a different craft from an email). Templates handle that badly. This is real
generation.

**The constraints, because this is a company chasing a person for money.**
Every generated message is validated before it can be sent:

- **Length**, per channel — an overflowing SMS silently becomes two, at double
  cost with a mangled second half.
- **No legal or credit threats** — no courts, police, CIBIL, blacklists,
  "defaulter", "final notice". A model asked to be persuasive drifts toward
  exactly this language, and debt-collection harassment rules exist.
- **No credential solicitation** — never an OTP, CVV, PIN, card number or
  password. This one is absolute: a legitimate merchant asking for an OTP over
  SMS is indistinguishable from the fraud that uses that same channel, and
  normalising it puts customers in danger.
- **No invented facts** — amount, merchant and next step come from the event.

A message that fails validation is **never sent**; a deterministic template goes
instead and the violation is recorded. The customer always gets a message. The
model is what makes it good, not what makes it possible.

## The offline default

`StubProvider` is the default: no API key, no network, no account. `git clone &&
python -m recoup backtest` produces the complete system on the first command.

This is not a fallback, it is a position. A reviewer should never have to buy an
API key to find out whether the thing works, and an LLM call in the hot path of
a payments engine is a latency and availability dependency you should have to
justify — not inherit by default.

The stub is not a no-op either: it does weighted keyword-evidence scoring
including Hindi and Hinglish terms, and it reports a real confidence margin, so
the confidence floor still does something meaningful offline. It correctly
classifies 5 of the 6 novel codes. The sixth is instructive — it got
`account_closed` *right* but clamped its own confidence to 0.45 because the text
contained "frozen", a cancellation hint, so the conservative profile stayed in
force. Refusing to be confident is the behaviour you want in this position.

What the stub cannot do is read a sentence it has no keywords for. That gap is
precisely the case for the real model, and `recoup triage --provider claude`
shows the difference on the same inputs.

## Honest limitations

- **The live Claude path is written and reviewed but not executed.** No API key
  was available while building this. `ClaudeProvider` forces structured output
  through a tool call and degrades on failure, and its contract is exercised
  against a fake provider in `tests/test_llm.py` — but it has not run against
  the real API, and I would not claim otherwise. Set `ANTHROPIC_API_KEY` and run
  `recoup triage --provider claude` to exercise it.
- **The confidence floor of 0.70 is a judgement, not a measurement.** Setting it
  properly needs a labelled set of genuinely novel codes, which requires
  production traffic.
- **The banned-content list is a denylist**, and denylists are never complete. It
  catches the failure modes I could anticipate. A production version wants a
  second model grading outbound messages, plus sampled human review.
